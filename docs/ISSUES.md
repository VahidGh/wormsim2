# wormsim2 — Issues & Improvements Tracker

A lightweight, version-controlled tracker for bugs, improvements, research questions,
and design decisions. Each item has a stable ID (`ISSUE-NNN`) so it can be referenced
from commits, code comments, and the requirements/design docs.

**Type:** `bug` · `improvement` · `research` · `decision` · `task`
**Status:** `open` · `in-progress` · `resolved` · `wontfix`
**Priority:** `P0` (blocker / core contribution) · `P1` (high) · `P2` (medium) · `P3` (low)

> IDs are never reused. When an item is resolved, move it to the **Resolved** section
> with a resolution note and date; do not delete it.

| ISSUE-013 | improvement | P2 | FEM body parallelisation for larger meshes | Current `FEMBody` uses UMFPACK direct solver on a serial `Triangulation` (2952 DOFs, ≈984 vertices). At this size, serial is optimal — factorisation is O(n^1.5) and the UMFPACK symbolic/numeric factorisation is done once at `init()`, leaving only cheap back-substitution per step. **Future trigger:** if the body mesh is refined for fluid–structure interaction (e.g. swimming requires per-vertex hydrodynamic drag), DOF count grows 10–100×. Then: (a) switch to `parallel::distributed::Triangulation` with MPI domain decomposition (deal.II native), (b) replace UMFPACK with Trilinos ML AMG preconditioner + CG iteration, (c) add `#pragma omp parallel for` on the element-assembly loop (currently serial in `FEMBody.cpp:160-197`). No action needed below ~30,000 DOFs. |
| ISSUE-014 | improvement | P2 | Tuner parallelisation: RFT speed estimate + C++ parameter sweep | `NeuromuscularTuner` currently runs a Python gradient loop over a 4-second real-data window. Two planned upgrades: **(A) Near-term** — add a Resistive Force Theory (RFT) forward-speed estimate from `theta_body` (Gray & Lissmann 1964 coefficients C_t, C_n). This gives a physics-based centroid velocity that can be validated against the Zenodo centroid track (ISSUE-007) without running the full FEM step; plug into the cost function as an additional loss term. **(B) Medium-term** — expose the parameter-space sweep as a C++ finite-difference Jacobian (`tuner_sweep.cpp`): run N forward simulations concurrently (OpenMP or MPI), finite-difference the cost-function gradient, and pass it back to the Python optimiser via pybind11. Enables ≥10× faster gradient computation for parameter vectors > ~20 dims. |
| ISSUE-015 | improvement | P2 | Tuner cost function: dynamic stratified frame selection | For simulations longer than the 4-second real-data window, evaluating every frame is expensive. Planned approach: (a) **stratified sampling** — divide the simulation into M = 20 non-overlapping windows; sample one frame randomly per window each iteration; ensures the full temporal range is covered with O(M) cost; (b) **importance weighting** — frames where the per-frame residual was high in the previous iteration are up-weighted (probability ∝ residual magnitude), focusing gradient steps on the hardest-to-fit regions; (c) exponential moving average of per-frame residuals as the importance weight signal (decay α ≈ 0.3 to adapt within ~3 iterations). Together this gives unbiased gradient estimates at O(M) cost vs O(N_total) for full evaluation. |

| ISSUE-017 | research | P0 | **[v0.13] Eigenworm-to-motoneuron mapping: infer IClamp drive from eigenworm trajectory** | **Core scientific goal:** each eigenworm transition detected in ISSUE-016 must be mapped to a corresponding change in motoneuron activation — this is what connects observed locomotion back to neural circuitry. The eigenworm coefficients are observables; the motoneuron IClamp parameters are the latent variables to infer. **Method and parameter map:** (A) *Forward crawl (high A, φ advancing):* DB1–DB7 and VB1–VB11 B-class motoneurons active; drive modeled as per-segment sinusoid with constant phase offset Δφ × k (k = segment index 0–23). Parameters to infer: `{ω_fwd [Hz], A_D [nA], A_V [nA], Δφ [rad/segment]}`. The spatial phase offset Δφ controls wave propagation speed (v_wave = ω / Δφ × L_body). (B) *Backward crawl (φ reversing):* A-class motoneurons DA1–DA9 + VA1–VA12 active (Chalfie et al. 1985; White et al. 1986 wiring); reverse phase offset −Δφ. AVA/AVE command neurons excite A-class; AVB/PVC inhibited. Parameters: `{ω_rev [Hz], A_D_rev, A_V_rev, Δφ_rev}`. (C) *Turn/omega:* SMD (dorsal head bending) + RMD (ventral) motoneurons activate asymmetrically; DD/VD cross-inhibition releases on one side. Parameters: `{A_SMD_D, A_SMD_V, t_dur_turn [s]}`. (D) *Amplitude modulation A(t):* maps to total excitatory drive scale factor `g_scale(t)` applied uniformly across all active segment IClamps. (E) *Wave speed dφ/dt:* maps to `ω`; typical N2 crawl 0.4–0.6 Hz (Stephens 2008). **Literature:** Boyle, Bryden & Cohen 2012 (PLoS CB) — definitive mechanistic body model; Fig 2 shows how IClamp sinusoid parameters (frequency, amplitude, phase offset) reproduce eigenworm limit cycles. Kato et al. 2015 — Fig 4: AVB activity predicts forward eigenworm amplitude; AVA predicts reversal; switching is ~1 s timescale. Nguyen et al. 2017 (PNAS) — shows proprioceptive body-bend feedback modulates ω to achieve wave-speed matching; relevant to Δφ inference. Zhen & Samuel 2015 (Curr Opinion Neurobiol) — review of command neuron → motoneuron → muscle topology. **Output:** per-behavioral-state parameter set `{ω, A_D, A_V, Δφ, g_scale(t)}` stored in `tuner_params.json`; time-varying `g_scale(t)` is the bridge between the eigenworm amplitude time series and the drive schedule fed to the HH model. |

| ISSUE-001 | decision | GPU compute backend | **Backend-agnostic core; OpenCL mandatory.** Three backends: **CPU/OpenMP** (portable reference — CI and correctness), **OpenCL** (mandatory GPU dev path — Intel Iris Plus 645 iGPU via macOS OpenCL.framework; also Linux iGPU/dGPU), **CUDA** (NVIDIA real-time/deploy target — RTX / HPC clusters). OpenCL is mandatory, not optional: it is the only GPU execution path available on the developer machine. Inside Docker on macOS, OpenCL headers compile but actual GPU dispatch requires running natively (macOS OpenCL.framework) or on a Linux host with GPU passthrough. Rationale: dev machine has no NVIDIA; CPU reference ensures correctness; OpenCL enables GPU validation on the dev iGPU. Supersedes the earlier optional-OpenCL decision. | 2026-06-15 |
| ISSUE-002 | decision | Body discretisation choice | **Corotated linear-elastic FEM on a tapered-cylinder tetrahedral mesh matching MetaWorm's body parameterisation.** deal.II 9.5.1 `FE_SimplexP<3>(1)` (P1 linear tets). Mesh generated via `GridGenerator::cylinder()` → `GridTools::convert_hypercube_to_simplex_mesh()` → targeted refinement to ≈984 vertices / ≈3,341 tetrahedra (MetaWorm-scale). Four muscle quadrants (D/V/L/R) × 24 longitudinal segments → 95 BWM activation constraints. Proprioceptive curvature feedback also lives in this layer. Prior wormuse hex/Cosserat approach not reused. | 2026-06-22 |
